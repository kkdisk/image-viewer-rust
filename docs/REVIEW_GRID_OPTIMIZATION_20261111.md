# 總覽縮圖與排序優化審查

日期：2026-11-11。範圍：HEAD `c3d60c5` 上六份產品程式的未提交修改；只審查、不修補產品程式。

## 發現

### P2：總覽尺寸選擇忽略圖片區寬度，全景圖仍可能放大

位置：`crates/app-ui/src/thumbnail_loader.rs:19`、`crates/app-ui/src/photo_browser.rs:319`。

`grid_thumbnail_edge` 只依 116 點高度與 DPI 選擇 256／384px，但總覽格子寬度會隨可用寬度與欄數變動；全景圖可能由寬度限制。以可用寬度 300 點、項目間距 8 點為例，一欄圖片區為 276×116 點，3:1 來源顯示為 276×92 點；200% DPI 需要 552×184px，目前只取得 384×128px，仍放大 1.4375 倍。

既有測試只覆蓋 3:2 來源，並將高度需求限制為最多 256px，未驗證不同長寬比與欄寬。以暫時整合回歸直接呼叫正式 `grid_thumbnail_edge(2.0)` 並套用現行格子幾何，確認測試失敗：目前長邊 384px，實際需要 552px；測試已移除。

建議依實際圖片區寬、高及 DPI 選擇有上限的長邊層級；若不讀取來源比例，可使用圖片區較長邊作保守需求。快取容量須配合評估。驗收至少涵蓋 3:2、方形、3:1 與欄數切換前後寬度。

### P3：資源契約未同步獨立總覽管理器

位置：`docs/SPEC_BROWSING_RESOURCES.md:7`、`docs/SPEC_PHOTO_BROWSER.md:29`，對照 `app.rs` 的 `grid_thumbnails` 初始化與 `ThumbnailManager::for_grid`。

現行契約仍記載兩個縮圖工作執行緒、單組 32 筆工作／結果通道及預設 16 MiB；新版本在應用建立時另啟動總覽管理器，實際為兩組各兩條工作、各自通道，紋理估計預算合計 80 MiB（膠卷 16＋總覽 64）。模式切換不取消另一組已排工作，可能同時解碼。預算仍不包含完整來源像素、通道中結果、上傳與驅動配置。

建議同步兩份契約，明載每組與合計資源，以及模式切換中的工作生命週期；不要將紋理預算表述為整個程序的記憶體上限。

## 其餘結論與驗證

- 未發現 `ensure_sort` 造成排序／篩選／選取回歸。來源掃描、metadata 更新及日期索引交付仍呼叫真正的 `set_sort`，刪除保留既有相對順序；安裝時可套用載入期間變更的排序條件。
- 尺寸切換會清除該管理器的快取並更新世代；範圍切換、重掃與刪除涵蓋兩組管理器。
- `cargo test --workspace --locked --offline` 通過；`cargo clippy --workspace --all-targets --locked --offline -- -D warnings` 通過。
- `cargo fmt --all -- --check` 與 `git diff --check` 通過。
- 上述全工作區測試通過與暫時回歸失敗是兩項不同結果；既有測試尚未涵蓋發現的全景圖情境。
- 未做原生 DPI／GPU／流暢度與工作集量測、發布建置、提交或推送。產品程式保持原狀。
