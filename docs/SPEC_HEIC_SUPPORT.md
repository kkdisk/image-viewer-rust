# HEIC／HEIF 支援規格（草案）

日期：2026-11-12。狀態：**草案第 3 版**。已納入審查的 5 項修正、使用者決策（第 7 節）與 [T0 技術驗證](SPIKE_HEIC_WIC.md) 結果；WIC 路線經實測可行。尚未授權實作，版本暫定 0.9.0。

## 1. 目標與範圍

讓手機（iPhone 等）拍攝的 `.heic`／`.heif` 照片可與現有格式一樣：開啟、瀏覽、縮圖列與總覽、EXIF 資訊與拍攝日期索引、查重、壓縮檔內瀏覽，以及編輯後另存為既有可寫格式。

AVIF（`.avif`）經使用者決定同批支援，走相同的容器判定與 WIC 路徑。

不在範圍：寫出 HEIC／AVIF、HDR／10 位元編輯與增益圖（gain map）色調映射、深度圖與輔助影像、連拍或原況照片的多影像瀏覽（只顯示主影像）。macOS 不在本版範圍，後續規劃見第 8 節。

## 2. 解碼路線

| 方案 | 做法 | 評估 |
|---|---|---|
| **A. Windows 內建解碼（WIC，建議，T0 驗證候選）** | 透過已在依賴中的 `windows` 0.62.2 呼叫 Windows Imaging Component；HEIF 容器由「HEIF 影像延伸模組」、HEVC 由「HEVC 影片延伸模組」提供 | 不新增 crate、不需原生建置；不散布 HEVC 解碼器；維持單一 exe 與 15 MB 限制。缺點是使用者須安裝延伸模組（HEVC 部分機型需付費或由 OEM 預裝），不同版本行為需實測，CI 執行器可能沒有解碼器。 |
| B. 內建 libheif（`libheif-rs`） | 隨程式附帶 libheif＋libde265 | **違反主規格**「不得引入含 C/C++ 外部動態連結依賴的 crate」及「單一可執行檔、無額外 DLL」驗收，另有 LGPL-3 與 HEVC 專利風險。除非主規格變更，否則不採用。 |
| C. 純 Rust 解碼器 | — | 就目前所知尚無成熟的純 Rust HEVC 解碼器，不可行（實作前再確認）。 |

T0 實測確認方案 A 可行（解碼、尺寸預檢、方向、色彩轉換、記憶體來源、背景執行緒皆通過），**採用方案 A**。

## 3. 架構與格式清單

### 3.1 模組邊界

- 依主規格，`core-image` 與 `core-archive` 是彼此獨立的底層模組，**不新增兩者之間的依賴**。
- `core-image` 定義兩份清單：**可讀格式** `READABLE_EXTENSIONS`（加入 `heic`、`heif`、`avif`）與**可寫格式** `WRITABLE_EXTENSIONS`（維持現有另存格式，不含 HEIC／HEIF）。app-ui 的播放清單、查重掃描、開檔篩選引用可讀清單；另存與匯出篩選引用可寫清單。
- `core-archive` 保留自己的壓縮檔內圖片副檔名常數（屬於解壓安全層的過濾規則），由 app-ui 新增**跨套件一致性測試**，斷言它與 `core_image::READABLE_EXTENSIONS` 相同，防止兩邊不同步。
- 回歸要求：HEIC／HEIF 不得出現在另存與匯出的格式篩選中。

### 3.2 解碼入口（全部需要分流）

`core-image` 中所有會用 `image` crate 讀取標頭或像素的公開 API 都要依格式分流，產品其他模組不直接呼叫 WIC：

| API | 用途 | HEIF 行為 |
|---|---|---|
| `inspect_animation` | 文件載入前置檢查（`document_io.rs` 先呼叫此函式再解碼） | 先檢查像素上限，回傳「非動畫」；不得因 `image` 無法辨識而提前失敗 |
| `load_image`、`load_image_with_limit` | 文件、縮圖、查重預覽、pHash | 依指定像素上限，經 WIC 解碼 |
| `load_image_from_memory`、`load_image_from_memory_with_limit` | 記憶體來源 | 以 WIC 串流（`IStream`）解碼並沿用上限；若 T0 顯示不可行則明確回傳不支援 |
| `inspect_dimensions`、`inspect_dimensions_from_memory` | 查重尺寸預檢等 | 經 WIC 取得尺寸，不解碼像素 |

資訊面板的格式標籤（`convenience.rs` 直接使用 `ImageReader`）改呼叫 `core-image` 提供的格式辨識函式。

### 3.3 容器與編碼判定

不得因 `ftyp` 品牌就推定是 HEVC：`mif1`／`msf1` 是 HEIF 通用品牌，AVIF 也會使用（見 [AOM AVIF 規格](https://aomediacodec.github.io/av1-avif/#avif-baseline-profile)）。判定分兩層：

1. **容器家族**：`ftyp` 的主品牌或相容品牌屬於 ISOBMFF 影像品牌，即視為 HEIF 家族。
2. **實際編碼**：以有界的 box 掃描讀取 `meta` 中的 `pitm`（主影像）與 `iinf`／`infe` 的項目類型判定：`hvc1` 為 HEVC，`av01` 為 AV1，`grid` 則依其分塊項目的類型判定；掃描失敗時再以相容品牌（`heic`／`heix`、`avif`／`avis`）輔助判定。掃描讀取量設上限，超過即視為無法判定。

錯誤對應：

| 判定結果 | 解碼元件狀態 | 使用者看到的訊息 |
|---|---|---|
| HEVC | 缺 HEIF 或 HEVC 延伸模組 | 需要安裝 HEIF／HEVC 延伸模組（附取得方式） |
| AV1 且已啟用 AVIF | 缺 AV1 延伸模組 | 需要安裝 AV1 延伸模組 |
| AV1 且未啟用 AVIF | — | 不支援 AVIF 格式（**不得**提示安裝 HEVC） |
| 其他或無法判定 | — | 不支援的 HEIF 編碼 |

## 4. 解碼行為契約

### 4.1 像素、色彩與方向

- 先取得尺寸並套用呼叫端指定的像素上限（預設 64M），再解碼像素；輸出一律為 8 位元 RGBA。
- **色彩**：轉成 8 位元不等於轉成 sRGB。T0 顯示 WIC 的 HEIF frame **不回報色彩內容**（`GetColorContexts` 為 0），所以來源色彩由 3.3 節的 box 掃描從主影像的 `colr` 屬性取得：
  - `prof`／`rICC`（ICC）：以 ICC 位元組建立來源色彩內容，目標為 sRGB（Exif 色彩空間 1），經 [IWICColorTransform](https://learn.microsoft.com/en-us/windows/win32/api/wincodec/nn-wincodec-iwiccolortransform) 轉換後才交付。T0 以 iPhone Display P3 樣本實測可行。
  - `nclx` 且色域為 sRGB／BT.709，或沒有 `colr`：直接交付。
  - `nclx` 且色域不是 sRGB（例如 P3），或任何轉換失敗：**降級**為不轉換直接顯示，並在資訊面板標示「色彩未轉換（來源為 ⟨色域⟩）」，不得靜默失敗。
  - 匯出時寫出的是已轉換的 sRGB 像素，不嵌入來源 ICC。此政策僅限 HEIF／AVIF；其他格式現行不做色彩管理，維持不變。
- **10 位元**：先完成色彩轉換再量化為 8 位元；不做 HDR 色調映射，不宣稱與「相片」App 的 HDR 呈現一致。
- **方向**：T0 確認 WIC **已套用** `irot`（樣本為 `irot 270°`，輸出為正確直式，`System.Photo.Orientation` 正規化為 1），但 EXIF Orientation 仍是 6。因此 HEIF／AVIF **一律略過 EXIF 方向校正**，以 WIC 輸出為準。`imir` 尚無樣本，驗收時需確認。資訊面板的「來源 EXIF 方向」照常顯示。

### 4.2 執行緒與錯誤

- COM 以每執行緒延遲初始化（MTA）處理；文件載入、縮圖、查重 rayon 執行緒都可能是首次呼叫者。T0 顯示未初始化的執行緒可能因程序的隱含 MTA 而「碰巧可用」，不得依賴。若執行緒已是 STA，初始化回傳 `RPC_E_CHANGED_MODE`，此時沿用既有模型、不反初始化（T0 確認工廠仍可用）。
- 新增 `ImageError::CodecMissing { codec }`，依 3.3 節對應訊息；縮圖沿用失敗節流，不反覆解碼。
- 非 Windows 平台可編譯，回傳「不支援的格式」。

## 5. EXIF、日期索引、儲存與效能

### 5.1 EXIF 與日期索引的讀取預算

- 拍攝時間、相機與時區沿用 `kamadak-exif` 0.5.5；它對 HEIF 使用可 Seek 的定位解析（依 `iloc` 跳到 Exif 區段），不需要整檔讀入。
- **512 KiB 的定義**：每檔**累計實際讀取位元組數**與**為該檔配置的緩衝總量**都不得超過 512 KiB；它**不是檔案位置上限**，讀取位置可以 Seek 到檔案後段。
- HEIF 採**有界 reader**：包裝檔案的 `Read + Seek`，累計讀取量超過預算即回傳錯誤；交給 `kamadak-exif` 解析時改傳此 reader，不先讀入固定長度的緩衝。JPEG 維持現行的漸進讀取。
- **配置上限**：T0 確認 `kamadak-exif` 以 `take(len).read_to_end` 讀取，**不依宣告長度預先配置**，並有 `MAX_EXIF_SIZE` 上限；有界 reader 即可同時限制讀取量與配置量，不需要預先掃描。iPhone 樣本實讀 16 KiB 即取得完整資訊；預算不足時回傳錯誤，不會 panic。
- **越界降級**：超過預算、解析失敗或沒有 DateTimeOriginal，一律列為「無可用拍攝日期」，與現行行為一致；不重試、不放寬預算。
- 原規劃的「自行解析 `meta`／`iloc` 定位 Exif」（舊 T5）改為：先評估有界 reader 搭配 `kamadak-exif`，只有 T0 證明不足時才自行實作。

### 5.2 儲存與輸出

- 不寫出 HEIC／AVIF。這類來源按「儲存」時改開「另存新檔」，預設同名 `.jpg`（使用者決定），並提示原檔不會被覆寫；篩選只列可寫格式（3.1 節）。
- 「儲存並繼續」等離開保護流程遇到 HEIC 來源時走同一流程；取消另存即取消離開。
- `save_image_atomic` 對 `.heic`／`.heif` 目標明確拒絕。輸出沿用「不保留來源 EXIF」契約。

### 5.3 效能與資源

- T0 實測 12MP 完整解碼約 410～495 ms（加色彩轉換約 725 ms），內嵌縮圖 240×320 只要約 29 ms；縮放解碼只省下約 25%，不採用。
- 縮圖：所需長邊不超過內嵌縮圖長邊時（縮圖列 80px、總覽 256 層級），使用內嵌縮圖，並套用相同的色彩轉換；其餘層級或沒有內嵌縮圖時，完整解碼後縮小（T6）。
- 封裝仍為單一 `app-ui.exe`；執行檔體積增量需在交付驗證中記錄。

## 6. 測試、驗收與風險

### 6.1 測試與驗收

- 自動化：
  - 容器家族與編碼判定：`heic`、`mif1`＋`hvc1`、`mif1`＋`av01`、`grid`、截斷或損毀的 box，以及錯誤訊息對應。
  - 以 PNG 走同一條 WIC 管線，驗證 COM、各入口（含 `inspect_animation`、自訂上限、記憶體來源）與 rayon 執行緒。
  - 有界 reader 的讀取量與配置上限，以及 Exif 位於檔尾的合成樣本。
  - 可讀與可寫清單的分離，以及 core-archive 一致性測試。
  - HEIC 來源的儲存與離開保護流程。
  - 偵測到元件時才執行的真實 HEIC 測試（方向、尺寸、色彩）；未安裝時明確略過並在驗證紀錄標示。
- 樣本：
  - 自動化測試用樣本，在元件存在時以 WIC HEIF 編碼器於測試執行中產生（T0 確認可建立編碼器），不提交二進位檔。
  - 真實樣本只用於本機與原生驗收，放在 `temp/`，不提交：iPhone 直式＋`irot`＋`grid`＋Display P3（已有一張）、橫式、`imir`、非 `grid`、10 位元、只有 `nclx`、sRGB、含深度圖、原況照片、`mdat` 在前、無 EXIF、損毀檔、AVIF。
  - 色彩驗收：P3 樣本轉換後與參考 sRGB 輸出比對，每通道平均差 ≤ 1、最大差 ≤ 4（參考值以同一 ICC 經 WIC 轉換產生，用於偵測回歸；不是跨引擎比對）。
- 原生驗收：開啟、縮圖列與總覽、方向、色彩、資訊面板、日期篩選、查重、ZIP 內 HEIC、另存，以及未安裝延伸模組與 AVIF 未啟用時的提示。

### 6.2 風險

| 風險 | 影響 | 緩解 |
|---|---|---|
| 使用者未安裝延伸模組（含 Windows N 版、Server） | 無法開啟 | 依編碼給出正確的錯誤與取得指引；不影響其他格式 |
| 延伸模組版本差異 | 行為、方向或色彩不一致 | T0 記錄測試版本；驗證紀錄附元件版本 |
| 重複旋轉 | 照片方向錯誤 | 4.1 節規則與直式樣本回歸 |
| 色彩轉換缺失或錯誤 | P3 照片偏色，匯出顏色錯誤 | 轉換與降級政策、色彩樣本驗收 |
| 通用品牌誤判 | 錯誤提示安裝 HEVC | 3.3 節兩層判定與錯誤對應測試 |
| COM 未初始化或執行緒模型衝突 | 背景解碼失敗 | 每執行緒初始化保護，加上 rayon 回歸 |
| WIC 在程序內解析不受信任的檔案 | 解碼器漏洞風險（與檔案總管相同） | 先檢查像素上限；不另外宣稱沙箱隔離 |
| Exif 位於檔尾或宣告長度異常 | 日期漏讀或過量配置 | 5.1 節的有界 reader、配置上限與降級 |

## 8. macOS（後續範圍，不在本版）

- macOS 的系統框架 ImageIO（`CGImageSource`）原生支援 HEIC（macOS 10.13 起）與 AVIF（macOS 13 起），**不需要另外安裝延伸模組**，因此沒有商店按鈕。系統框架會處理方向與色彩，與 WIC 路線的概念相同。
- 架構預留：core-image 的 HEIF 模組以平台後端區分（Windows 為 WIC），容器判定（3.3 節）、有界 EXIF 讀取（5.1 節）、錯誤類型與入口分流都與平台無關；macOS 只需新增一個後端。
- 前提與限制：整個程式目前尚未移植 macOS（中文字型、圖片剪貼簿、CI 與封裝都未處理）。macOS 後端需要使用系統框架的 Rust 繫結（例如 `objc2` 系列），屬於新依賴。系統框架不是隨程式附帶的 C/C++ 函式庫，但是否符合主規格的依賴條款需要另外確認。本機沒有 Mac，無法驗證，以上僅為依官方文件的規劃。
